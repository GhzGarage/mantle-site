Scripts you can share

A script package is a folder of scripts that you publish once and any creator can add to their own place, without opening or copying the code. A Script Point is a marker you drop in the level to tell a package where to act, with settings of its own. For example, a hazard package runs one script, and each Script Point marks one danger zone with its own size and damage.

How it works Live

  • Make it: put a folder in Packages/, next to your level's Scripts/ folder. It holds a small package.json and the same Server/, Client/ and Shared/ folders you already use for scripts.
  • Try it: Test Locally runs the level's packages along with its own scripts, so you can prove a package before you publish it. See Testing a package.
  • Publish it: when your place goes live, each package is published to the Mantle library too, as public or private, the same choice you make for vehicles and weapons.
  • Use someone else's: get a public package from the ASSETS tab in Mantle or from Tools → Mantle → Library... in Unreal, add it to your place's storage, and it runs in your place.
  • Add Script Points: drop them where the package should act, and set each point's parameters in the Details panel.

A place that uses script packages or Script Points needs script API 1.36. You don't set this yourself: Mantle raises the place's script API version to 1.36 for you when the place has a package (in the level's Packages/ folder or stored in Place Settings → Storage) or a Script Point.

A package's scripts run once per side (once on the server, once on each player's machine), not once per Script Point. The scripts loop over their points with Script.Points. A stored package with no Script Points still runs, which suits things that apply to the whole place, such as a double jump.

Making a package

Each folder inside Packages/ is one package. The folder's name is the name your place stores the package under, the name Script Points pick and the name other scripts use to reach it.

A level with one package
Content/MyPlace/
  MyPlace.umap
  Scripts/               the place's own scripts
    Server/
      Rounds.luau
  Packages/
    Hazards/             one package, stored as "Hazards"
      package.json       its name, description, parameters and settings
      Server/            runs on the server, once
        Main.luau
      Client/            runs on each player's machine, once
        Warning.luau
      Shared/            modules both sides (and the place) can require
        Config.luau
  • The folder name is a letter followed by up to 63 letters, digits or _, with no spaces, for example Hazards or Kill_Bricks. Don't name a package Shared, Server or Client: require("@Shared/...") would then reach the package instead of your own Shared folder. Check this place doesn't catch this, so keep to it yourself.
  • Files follow the same rules as your Scripts folder: Server/, Client/ and Shared/ spelled exactly, any folders inside them, and .luau/.lua, .ts, .js or .py files. Shared/ and any Modules folder only hold modules, which run when something requires them.
  • TypeScript is compiled when you publish, and the package is published as the resulting JavaScript.
  • Visual scripts: a graph saved inside a package runs and publishes as the Luau saved beside it, with a warning to remind you. Save the graph after every change so its Luau is up to date.
  • A package holds 1 to 64 scripts. Paths can use only the letters A to Z, digits, _, . and - (no spaces), must be unique even ignoring capital letters and are at most 200 characters. A script's name, its file name without the extension, is 1 to 80 characters.

package.json

The manifest names the package and lists what a Script Point can set.

Packages/Hazards/package.json
{
  "name": "Hazard Zones",
  "description": "Players inside a zone take damage every half second. Put a Script Point in the middle of each zone.",
  "parameters": [
    { "name": "Radius", "type": "number", "default": 300, "help": "How far the zone reaches, in centimeters." },
    { "name": "Damage", "type": "number", "default": 10, "help": "Damage each half second." },
    { "name": "Message", "type": "string", "default": "Danger!", "help": "Shown to a player who walks in." }
  ]
}
KeyRules
nameRequired. 1 to 64 characters on one line. This is what other creators see in the library.
descriptionOptional. Up to 1,000 characters.
parametersOptional. Up to 16 values that each Script Point sets for itself (see below).
settingsOptional. Up to 16 values set once for the whole package in each place that stores it. See Package settings.

Parameters and settings are written the same way. Each one is an object with these keys:

KeyRules
nameA letter followed by up to 31 letters, digits or _. Names in one list must be different even ignoring capital letters (Speed and speed clash).
type"string", "number", "boolean" or "choice".
defaultWritten as its type: 100 for a number, true or false for a boolean, text in quotes for a string or a choice (a choice's default is one of its options). At most 256 characters, with no space at the start or end. A number, boolean or choice needs a default unless it's marked "required": true, so a place that leaves it out still has a value.
requiredtrue or false (the default). A required value with no default must be set by the place, or the place can't be published. A required value that has a default is satisfied by the default.
min, maxNumbers only, both optional: the lowest and highest value allowed. min can't be above max, and the default must fit between them.
optionsChoices only: 2 to 32 different entries, each 1 to 64 characters.
helpOptional, up to 200 characters on one line. It shows beside the value in the Details panel.

Other keys in package.json are ignored.

A package's script

This server script runs once and checks every zone. Each Script Point is an entity at the point's position, and its parameters are read with GetAttribute, already turned into numbers and true/false as the manifest declares them. A player's Position is nil while they respawn, so the script checks it first.

Packages/Hazards/Shared/Config.luau
return { DamageScale = 1 }
Packages/Hazards/Server/Main.luau
local Config = require("Config")   -- this package's Shared/Config.luau

while true do
	for _, player in Players:GetPlayers() do
		for _, zone in Script.Points do
			if player.Position and (player.Position - zone.Position).Magnitude < zone:GetAttribute("Radius") then
				player:TakeDamage(zone:GetAttribute("Damage") * Config.DamageScale)
			end
		end
	end
	task.wait(0.5)
end

Inside a package, a bare name like require("Config") looks only in the package itself. A package can't reach the place's own scripts, and the place's scripts reach a package's modules with require("@Hazards/Config"). They talk to each other through Events, State and Net. See Script packages and Script Points.

Testing a package

Test Locally can't fetch library items, so a package you stored from another creator doesn't run there. The Mantle Preview panel warns "This place stores library items (Place Settings > Storage); a preview cannot fetch them, so it runs without." To try a package, put it in the level's Packages/ folder. Test Locally runs every package in that folder exactly as a stored one would, along with its Script Points and their typed parameters, even before the package has been published or stored. A place file you've exported to disk and launch by itself can also use a package that's only in the Packages/ folder beside it; the log says so with a line starting "MANTLE_SCRIPT_PACKAGE '[name]' is not in the place's storage".

Publishing a package Live

You don't publish a package on its own. When you publish your place:

  1. Upload

    Every file in each package uploads with the place's own scripts and is screened the same way. Files you've uploaded before aren't sent again.

  2. Choose who can use it

    The Mantle Publish tab asks "Vehicles, weapons and script packages in this place: who can use them". Public lists the package in the library for every creator and needs the rights declaration ticked. Private means only you can use it.

  3. It becomes a library item

    The first publish creates the package's library item. A later publish adds a new version only if a file or package.json changed; otherwise the place is pinned to the version that already matches. If you change the Public or Private choice, the library item changes to match.

  4. Your place stores it

    Each package is added to Mantle Place Settings → Storage under its folder's name, pinned to that version. If the place already stores an entry with that name, it moves to that version and keeps its settings. The Output Log says: "N published script package(s) are now stored in Place Settings > Storage".

  • Save to Mantle doesn't publish packages. A draft leaves out the Script Points of packages that aren't stored yet, and says so: "Script packages become library items when you publish; until then the draft leaves out N Script Point(s) that use them (…)".
  • If Mantle is still screening a package's scripts, nothing goes live: "Mantle is still screening the scripts of package '…', so nothing went live yet. Choose Publish again in a minute; nothing is uploaded twice."
  • A package can have up to 256 versions. After that: "The package '…' already has as many versions in your library as Mantle allows, so nothing went live. Copy it to a package folder with a new name (a new name makes a new library item), then publish again."
  • Packages share the place's storage with vehicles and weapons: 32 entries in all. "This place would store N library items with its script packages, and a place stores at most 32. Remove some from Place Settings > Storage, or combine packages."

Using another creator's package Live

  1. Look before you get it

    In Mantle's ASSETS tab, a package's details list its files and let you read every one before you get it. What you read is exactly what runs.

  2. Get it

    Press Get in the ASSETS tab, or in Unreal open Tools → Mantle → Library..., choose Scripts and All, and press Get. Everything is free for now.

  3. Add it to storage

    In the Library panel, choose Mine and press Add to storage on the package. It's stored under a name made from the package's name (spaces and symbols become _, so "Kill Bricks" becomes Kill_Bricks; a name that starts with a digit gets Item_ first, and a number such as _2 is added if that name is taken), pinned at its latest version. You can rename the entry in Place Settings → Storage.

  4. Place Script Points, if it uses them

    See Script Points. A package that needs none just runs once the place is published.

  • Your place never changes by itself. It runs the version it pinned until you choose Update to vN in the Library panel or Update to latest on the storage row. Publishing never changes the pin of a package you got from someone else. A package of your own in Packages/ is pinned to the version you just published.
  • To stop using a package, press Remove on its row in the Library panel's storage list.
  • If Mantle takes a package down, it stops running in every place that stores it.
  • A package runs with exactly the abilities a place script has on its side, nothing more, and its scripts have the same limits as any other script.

Script Points Live

Choose Tools → Mantle → Add Script Point. The point appears in front of you in the viewport, with the package's name floating above it in the editor (players never see a Script Point). In its Details panel:

FieldWhat it does
Storage ItemA dropdown of the place's script packages: stored packages first, then packages in the level's Packages/ folder that aren't stored yet ("(in Packages/, stored when you publish)"), then any storage entry typed in by hand. If there are none: "This place has no script package. Add one with Tools > Mantle > Library (Scripts), or make one in a Packages folder beside the level's Scripts folder."
ParametersOne row for each parameter the package declares, labeled with its name and type (for example "Speed (number, 1 to 10, required)"), its help text, and its default as a hint. The row is a text box for a string or a number, a slider for a number with both a min and a max, a checkbox for a boolean and a dropdown for a choice. Default clears the value, so the package's default applies. A red note under the name flags a value that doesn't fit, or a required parameter with no value: "Hazards needs Radius."
EnabledUntick to keep the point in the level without the package's scripts seeing it.

The point's position and rotation are what the scripts see. A place can have up to 64 Script Points, each setting up to 16 parameters, and each value can be up to 256 characters.

Package settings Live

A package can also declare settings: values set once for the whole package in each place that stores it, such as a round length or a difficulty. Parameters belong to one Script Point; settings belong to the package. Both use the keys in package.json.

Packages/Hazards/package.json (part)
"settings": [
  { "name": "RoundLength", "type": "number", "default": 120, "min": 30, "max": 600, "help": "Seconds before the zones reset." },
  { "name": "Difficulty", "type": "choice", "options": ["Easy", "Normal", "Hard"], "default": "Normal" },
  { "name": "ShowWarnings", "type": "boolean", "default": true }
]

A package declares up to 16 settings.

  • Setting them: select Mantle Place Settings and open its Storage list. A stored package's row shows one row per setting, drawn the same way as a Script Point's parameters (text box, slider, checkbox or dropdown, with a Default button and a red note when something's wrong, such as "KillBricks needs RoundLength."). The values publish with the place, and the place keeps them with the version it pins. Scripts read them as Script.Settings.
  • Your own package's first publish: a package in your Packages/ folder only gets a storage row once the place has published it, so you can't set its settings before then. Give every required setting a default in package.json, or Check this place and the first publish both stop. Check this place says: "Packages/… is stored with no settings when the place first publishes it: give that setting a default in its package.json."
  • New versions: when you update a package to a version that no longer declares a setting, that setting's value is dropped from the storage entry, and the Output Log says which ("MANTLE_STORAGE package '…' version N no longer declares the setting(s) …; dropped from its storage entry").
