Scripts you can share

A script package is a folder of scripts that you publish once and any creator can add to their own place, without opening or copying the code. A Script Point is a marker you drop in the level to tell a package where to act, with settings of its own. For example, a hazard package runs one script, and each Script Point marks one danger zone with its own size and damage.

How it works Live

  • Make it: put a folder in Packages/, next to your level's Scripts/ folder. It holds a small package.json and the same Server/, Client/ and Shared/ folders you already use for scripts.
  • Try it: Test Locally runs the level's packages along with its own scripts, so you can prove a package before you publish it.
  • Publish it: when your place goes live, each package is published to the Mantle library too, as public or private, the same choice you make for vehicles and weapons.
  • Use someone else's: get a public package from the ASSETS tab in Mantle or from Tools → Mantle → Library... in Unreal, add it to your place's storage, and it runs in your place.
  • Anchor it: drop Script Points where the package should act, and set each point's parameters in the Details panel.

A package's scripts run once per side (once on the server, once on each player's machine), not once per Script Point. The scripts loop over their points with Script.Points. A stored package with no Script Points still runs, which suits things that apply to the whole place, such as a double jump.

Making a package

Each folder inside Packages/ is one package. The folder's name is the name your place stores the package under, the name Script Points pick and the name other scripts use to reach it.

A level with one package
Content/MyPlace/
  MyPlace.umap
  Scripts/               the place's own scripts
    Server/
      Rounds.luau
  Packages/
    Hazards/             one package, stored as "Hazards"
      package.json       its name, description, parameters and settings
      Server/            runs on the server, once
        Main.luau
      Client/            runs on each player's machine, once
        Warning.luau
      Shared/            modules both sides (and the place) can require
        Config.luau
  • The folder name is a letter followed by up to 63 letters, digits or _, with no spaces, for example Hazards or Kill_Bricks. Don't name a package Shared, Server or Client: require("@Shared/...") would then reach the package instead of your own Shared folder.
  • Files follow the same rules as your Scripts folder: Server/, Client/ and Shared/ spelled exactly, any folders inside them, and .luau/.lua, .ts, .js or .py files. Shared/ and any Modules folder only hold modules, which run when something requires them.
  • TypeScript is compiled when you publish, and the package is published as the resulting JavaScript.
  • Visual scripts: a graph saved inside a package runs and publishes as the Luau saved beside it, with a warning to remind you. Save the graph after every change so its Luau is up to date.
  • A package holds 1 to 64 scripts. Paths must be unique even ignoring capital letters, and each is at most 200 characters.

package.json

The manifest names the package and lists what a Script Point can set.

Packages/Hazards/package.json
{
  "name": "Hazard Zones",
  "description": "Players inside a zone take damage every half second. Put a Script Point in the middle of each zone.",
  "parameters": [
    { "name": "Radius", "type": "number", "default": 300, "help": "How far the zone reaches, in centimetres." },
    { "name": "Damage", "type": "number", "default": 10, "help": "Damage each half second." },
    { "name": "Warning", "type": "string", "default": "Danger!", "help": "Shown to a player who walks in." }
  ]
}
KeyRules
nameRequired. 1 to 64 characters on one line. This is what other creators see in the library.
descriptionOptional. Up to 1,000 characters.
parametersOptional. Up to 16 values that each Script Point sets for itself (see below).
settingsOptional. Up to 16 values set once for the whole package in each place that stores it. See Package settings (script API 1.36).

Each parameter is {"name", "type", "default", "help"}:

  • name: a letter followed by up to 31 letters, digits or _. Each name appears only once.
  • type: "string", "number" or "boolean". From script API 1.36 also "choice", with the extra keys described under Package settings.
  • default: written as its type: 100 for a number, true or false for a boolean, text in quotes for a string. A number or boolean parameter must have a default, so a point that leaves it out still has a value. At most 256 characters, with no space at the start or end.
  • help: optional, up to 200 characters on one line. It shows beside the parameter in a Script Point's Details panel.

Other keys in package.json are ignored.

A package's script

This server script runs once and checks every zone. Each Script Point is an entity at the point's position, and its parameters are read with GetAttribute, already turned into numbers and true/false as the manifest declares them.

Packages/Hazards/Shared/Config.luau
return { DamageScale = 1 }
Packages/Hazards/Server/Main.luau
local Config = require("Config")   -- this package's Shared/Config.luau

while true do
	for _, player in Players:GetPlayers() do
		for _, zone in Script.Points do
			if (player.Position - zone.Position).Magnitude < zone:GetAttribute("Radius") then
				player:TakeDamage(zone:GetAttribute("Damage") * Config.DamageScale)
			end
		end
	end
	task.wait(0.5)
end

Inside a package, a bare name like require("Config") looks in the package itself first. A package can't reach the place's own scripts, and the place's scripts reach a package's modules with require("@Hazards/Config"). They talk to each other through Events, State and Remotes. See Script packages in scripts.

Testing a package

Test Locally runs every package in the level's Packages/ folder exactly as a stored one would, along with its Script Points, even before the package has been published or stored. In Test Locally, a Script Point's parameters reach your scripts as text; once the place is published they arrive as the type the manifest declares.

Publishing a package Live

You don't publish a package on its own. When you publish your place:

  1. Upload

    Every file in each package uploads with the place's own scripts and is screened the same way. Files you've uploaded before aren't sent again.

  2. Choose who can use it

    The Mantle Publish tab asks "Vehicles, weapons and script packages in this place: who can use them". Public lists the package in the library for every creator and needs the rights declaration ticked. Private means only you can use it.

  3. It becomes a library item

    The first publish creates the package's library item. A later publish adds a new version only if a file or package.json changed; otherwise the place keeps the version it has.

  4. Your place stores it

    Each package is added to Mantle Place Settings → Storage under its folder's name, pinned to that version: "N published script package(s) are now stored in Place Settings > Storage".

  • Save to Mantle doesn't publish packages. A draft leaves out the Script Points of packages that aren't stored yet, and says so: "Script packages become library items when you publish; until then the draft leaves out N Script Point(s) that use them (…)".
  • If Mantle is still screening a package's scripts, nothing goes live: "Mantle is still screening the scripts of package '…', so nothing went live yet. Choose Publish again in a minute; nothing is uploaded twice."
  • A package can have up to 256 versions. After that: "The package '…' already has as many versions in your library as Mantle allows, so nothing went live. Copy it to a package folder with a new name (a new name makes a new library item), then publish again."
  • Packages share the place's storage with vehicles and weapons: 32 entries in all. "This place would store N library items with its script packages, and a place stores at most 32. Remove some from Place Settings > Storage, or combine packages."

Using another creator's package Live

  1. Look before you get it

    In Mantle's ASSETS tab, a package's details list its files and let you read every one before you get it. What you read is exactly what runs.

  2. Get it

    Press Get in the ASSETS tab, or in Unreal open Tools → Mantle → Library..., choose Scripts and All, and press Get. Everything is free for now.

  3. Add it to storage

    In the Library panel, choose Mine and press Add to storage on the package. It's stored under a name made from the package's name (spaces become _, so "Kill Bricks" becomes Kill_Bricks, with a number added if that name is taken), pinned at its latest version. You can rename the entry in Place Settings → Storage.

  4. Place Script Points, if it uses them

    See Script Points. A package that needs none just runs once the place is published.

  • Your place never changes by itself. It runs the version it pinned until you choose Update to vN in the Library panel or Update to latest on the storage row. Publishing never changes a pin.
  • To stop using a package, press Remove on its row in the Library panel's storage list.
  • If Mantle takes a package down, it stops running in every place that stores it.
  • A package runs with exactly the abilities a place script has on its side, nothing more, and its scripts have the same limits as any other script.

Script Points Live

Choose Tools → Mantle → Add Script Point. The point appears in front of you in the viewport, with the package's name floating above it in the editor (players never see a Script Point). In its Details panel:

FieldWhat it does
Storage ItemA dropdown of the place's script packages: stored packages first, then packages in the level's Packages/ folder that aren't stored yet ("(in Packages/, stored when you publish)"). If there are none: "This place has no script package. Add one with Tools > Mantle > Library (Scripts), or make one in a Packages folder beside the level's Scripts folder."
ParametersOne row for each parameter the package declares, shown as "Name (type)" with its help text and its default as a hint. Tick Default to leave a parameter out of this point, so the package's default applies.
EnabledUntick to keep the point in the level without the package's scripts seeing it.

The point's position and rotation are what the scripts see. A place can have up to 64 Script Points, each setting up to 16 parameters, and each value can be up to 256 characters.

Package settings Live

From script API 1.36, a package can also declare settings: values set once for the whole package in each place that stores it, such as a round length or a difficulty. Parameters belong to one Script Point; settings belong to the package.

Packages/Hazards/package.json (part)
"settings": [
  { "name": "RoundLength", "type": "number", "default": 120, "min": 30, "max": 600, "help": "Seconds before the zones reset." },
  { "name": "Difficulty", "type": "choice", "options": ["Easy", "Normal", "Hard"], "default": "Normal" },
  { "name": "ShowWarnings", "type": "boolean", "default": true },
  { "name": "TeamName", "type": "string", "required": true, "help": "The team the zones belong to." }
]
KeyRules
name, helpAs for parameters.
type"string", "number", "boolean" or "choice".
defaultWritten as its type; for a choice, one of its options.
requiredtrue means a place must give it a value if there's no default.
min, maxNumbers only: the lowest and highest value allowed.
optionsChoices only: 2 to 32 entries to pick from.

A package declares up to 16 settings. Script Point parameters can use the same choice, min, max and required keys.

To set a stored package's settings, select Mantle Place Settings and open its Storage list. The package's row shows one control per setting: a dropdown for a choice, a slider for a number with a min and max, a checkbox for a boolean, and a text box otherwise. The values publish with the place and stay with the version it pins. Scripts read them as Script.Settings.
