Server, client, shared

The server owns the game: it moves things for everyone, keeps score and decides who wins. A client script runs on one player's machine and handles what that player sees: HUD, toasts, local effects.

Every part of the API exists on both sides, so types and autocomplete are the same everywhere. But some members only work on one side. If you call one on the wrong side, you get a clear error like this one (that's the Luau text; other languages spell the member their own way, such as UI.toast in JavaScript):

UI:Toast can only be called from the client.

Server changes reach everyone

  • Setting Position, Visible and similar, tweens, attributes, tags, clones and destroys are all synced from the server to every player, including players who join later. (This is called replication.)
  • State:Set, teleporting and kicking players.
  • Firing remotes to one player or all of them.

Client changes are local

  • Setting a property of an entity (the object your script uses to work with an actor in the world) on a client changes only that player's view, as on Roblox. When the server next changes it, the server's value wins.
  • HUD text and toasts. UI:Toast(text, seconds?) shows a message at the top center of the screen for 1 to 10 seconds (3 by default), replacing the one before it. UI:SetText(slot, text) keeps a named line at the top left: the same slot replaces its line, empty text clears it, and up to 8 lines show at once. Both are plain text with no line breaks, and anything past 120 characters is cut off. A ninth line is refused until you clear one. For anything bigger, build UI documents or UI nodes.
  • Players.LocalPlayer is always set in a client script: client scripts start once the local player exists.
  • Asking the server for things with Remote:FireServer.

Server scripts are private: only the creator who uploaded one, and the owner of a place or package that uses it, can read its source. Players never get it. Client and shared scripts are unchanged: a player's machine runs them, so treat their source as public.

In a session, server scripts run on the server and client scripts run on each player's machine as they join. Test multiplayer behavior by publishing and joining with the Mantle client, and include a player who joins late. Scripts don't run in the editor's Play (PIE) mode: to try them on your own PC first, use Tools → Mantle → Test Locally (see Testing with Test Locally).

Give actors a tag in the editor, then write one script for every actor with that tag. These examples use the tag guide_code_killbrick. The script covers every tagged actor already placed and any added later, clones included. You never need to attach a script to an actor.

World:OnTagged("guide_code_killbrick", function(brick)
	brick.Touched:Connect(function(player)
		player:Teleport(Vector3.new(0, 0, 150))
	end)
end)

Signals: reacting to things

When something happens in the game, it fires a signal, such as Touched, PlayerAdded, State.Changed or a remote's event. Connect a function to a signal to react to it. Each call runs on its own, so a handler can wait without holding up anything else.

MemberWhat it does
Connect(fn) → ConnectionCall fn every time it fires.
Once(fn) → ConnectionCall fn the next time only.
Wait()Pause until it fires, then return its arguments. In JavaScript it returns a Promise that resolves with the value itself when the signal fired with one argument, and with an array when it fired with more. In Python, it only works inside a generator (a function containing yield): save token = signal.wait(), yield that token, then read token.result, which is always a tuple of all the arguments.
Connection:Disconnect()Stop listening. Everything a script connected is disconnected automatically when the script stops.
Fire(...)Only for your own events from Events:Get(name). Built-in signals can't be faked.

Signals that report a change pass the old value first, then the new one: Player.HealthChanged(player, old, new) and Player.StaminaChanged(player, old, new) (API 1.40), Teams.PlayerTeamChanged(player, old, new) and Match.StateChanged(old, new) (API 1.39). Some others pass the key and the new value instead: State.Changed(key, value) and AttributeChanged(name, value).

Waiting and timers

Every language can pause without freezing the game. Each one uses the style its programmers already know:

Luau · like Roblox
task.wait(2)                        -- pause this thread 2 s
task.spawn(function() ... end)      -- run now, in parallel
task.delay(5, function() ... end)   -- run in 5 s
local thread = task.delay(9, boom)
task.cancel(thread)                 -- never mind
TypeScript · async/await
await task.wait(2);                  // inside an async function
task.spawn(async () => { ... });
const id = task.delay(5, () => { ... });
task.cancel(id);
setTimeout(() => { ... }, 500);       // web-style timers work too
JavaScript · async/await
await task.wait(2);                  // inside an async function
task.spawn(async () => { ... });
const id = task.delay(5, () => { ... });
task.cancel(id);
setTimeout(() => { ... }, 500);       // web-style timers work too
Python · generators (like Unity coroutines)
def countdown():
    for n in range(3, 0, -1):
        print(n)
        yield task.wait(1)        # a function that yields can wait
    print("go!")

task.spawn(countdown)             # start it
task.delay(5, lambda: print("5 s later"))

def wait_for_join():
    token = Players.player_added.wait()
    yield token                   # waits for the signal
    player = token.result[0]      # what it fired with
Long loops must wait

Each script has a limited share of CPU time and memory: 8 milliseconds of CPU time in any second, and 16 MiB of memory. If a script goes over either budget, or hits a host limit, Mantle stops that script, along with its tasks and connections. Split long work into chunks with waits in between.

A single run that goes too long without waiting is cut short too. In Luau and JavaScript you see "script exhausted its instruction budget (100000 instructions since it last yielded). Break long loops up with task.wait()." Python shows the same message without the count.

In Python, an operation that would take a script over its memory budget is refused, and the script is stopped.

Each script can also have up to 64 timers waiting at once (task.wait, task.delay, task.defer, setTimeout and setInterval count) and up to 256 signal connections.

Values

Pass ordinary values of your language: numbers, strings, booleans, lists, tables/objects/dicts, Vector3, entities and players. They go into State, attributes and remotes as they are, and come back the same way. Functions can't be stored or sent: State:Set stops with "State can't hold functions", and a value nested more than 16 levels deep stops with "State values can't be nested more than 16 levels".

State:Set("round", { number = 3, leader = "ana", spawn = Vector3.new(0, 0, 200) })
local round = State:Get("round")
print(round.number, round.spawn.Z)          -- 3  200
State.set("round", { number: 3, leader: "ana", spawn: new Vector3(0, 0, 200) });
const round = State.get("round");
console.log(round.number, round.spawn.z);    // 3 200
State.set("round", { number: 3, leader: "ana", spawn: new Vector3(0, 0, 200) });
const round = State.get("round");
console.log(round.number, round.spawn.z);    // 3 200
State.set("round", {"number": 3, "leader": "ana", "spawn": Vector3(0, 0, 200)})
r = State.get("round")
print(r["number"], r["spawn"].z)             # 3 200

Positions are in centimeters (100 = 1 m), like Unreal. Rotations are Vector3(pitch, yaw, roll) in degrees.

A script can only move, rotate or scale a dynamic entity. A level actor is dynamic when you set it to Movable in the editor. Entities a script spawns or clones are dynamic already. Moving, rotating, scaling or tweening any other entity raises an error, for example can't set Position on an entity that isn't dynamic; mark it "dynamic": true in the place (or Clone it, since a clone can move). A tween says can't tween Position, Rotation or Scale on an entity that isn't dynamic; mark it "dynamic": true in the place. See Errors and limits.

Sharing code

Put reusable code in Shared/ (both sides) or a Modules/ folder (that side only), then load it from your scripts. A leading @Shared/ is optional and works in every language when Mantle runs your scripts. Only the Luau and TypeScript code editors also know it, so only they autocomplete it.

Scripts/Shared/Modules/Examples/Config.luau
return { RoundSeconds = 60, SpawnPoint = Vector3.new(0, 0, 150) }
Scripts/Server/ReadConfig.luau
local Config = require("@Shared/Modules/Examples/Config")
Scripts/Shared/Modules/Examples/Config.ts
export const roundSeconds = 60;
Scripts/Server/ReadConfig.ts
import { roundSeconds } from "@Shared/Modules/Examples/Config";
console.log(roundSeconds);
Scripts/Shared/Modules/Examples/Config.js
export const roundSeconds = 60;
Scripts/Server/ReadConfig.js
import { roundSeconds } from "@Shared/Modules/Examples/Config";
Scripts/Shared/Modules/Examples/Config.py
ROUND_SECONDS = 60
Scripts/Server/ReadConfig.py
Config = require("@Shared/Modules/Examples/Config")   # the module itself, loaded once
print(Config.ROUND_SECONDS)

Each labeled block is a separate file. Type Shared/Modules/Examples/Config exactly as shown: paths must match capital letters exactly, on Windows as well as Linux.

  • A Modules folder nested inside another folder still only holds modules.
  • If the capitalization is wrong, or you require an entry script (a script that runs on its own rather than a module), you get a clear error. A path outside Scripts isn't found. You can leave off the file extension.
  • A path starting with ./ or ../ is relative to the file that asks for it. Any other path starts from Scripts/, and is also tried under Shared/ and under the asking script's own side.
  • Luau and Python modules must finish loading without waiting. In Luau, a module that calls task.wait while loading gives "require: <path> waited while loading; modules must finish loading without task.wait".
  • In Luau and Python, circular requires (modules that require each other in a loop) are an error: "require: <path> requires itself (directly or through another module)".
  • Dynamic import() is blocked in JavaScript and TypeScript: "dynamic import() is not available to Mantle scripts; use a static import instead".
  • A module is loaded once and reused. In Luau and Python it's shared by the scripts on a side; in JS/TS each script gets its own copy.
  • Python uses require(...) rather than import for your own files: it returns the module object (or the value of __export__ if the module sets one), so Config.ROUND_SECONDS works as usual. Python's own built-in modules (like math) still use import.
  • Client scripts can't load server code; it never leaves the server. Server scripts can't load client code.
  • A script package your place stores has its own modules: reach its Shared/ modules with require("@Name/Module") (the package's own scripts can use its name the same way). See Script packages.
  • Luau and Python can only load files in their own language; JavaScript and TypeScript can import each other. Give modules unique names across languages, since an extensionless path can match a file in another language. To share between languages, use State, Events or a Remote (see Mixing languages).

Remotes are for one-off messages. Get one with Net:Remote(name). A remote is a named channel with FireServer (client to server), and FireClient / FireAllClients (server to clients). On the server, you receive with the remote's OnServerEvent signal, and the handler's first argument is the player who actually sent the message. On a client, use OnClientEvent.

Up to 256 messages per remote that arrive before a handler connects are held for it, and the oldest are dropped past that (see Errors and limits). But a remote doesn't store anything, and it doesn't replay earlier messages to players who join late. Put things like the current score, round and door status in State instead.

Never trust a client

A client can send anything. When a message says “I pressed the button”, check on the server that the player really is near the button, as in the button recipe.

Mixing languages

Scripts in different languages share one world. They talk through the same three channels, which work the same way in every language:

  • State (with the Changed signal) for shared values.
  • Events: Events:Get("GoalScored") is a named signal for scripts on the same side. Any script can Fire it or connect to it.
  • Remotes between server and clients.

The checkpoint recipe shows how: the checkpoint script writes a respawn position into State, and the kill brick script reads it when a player touches a hazard. They only share State, so you can write the checkpoints in TypeScript and the kill brick in Luau, and neither imports the other's module.

Assets your scripts use

A script can only spawn a mesh, show a material or play a sound that was published with the place. Anything placed in the level is published automatically. For an asset nothing in the level uses, such as a projectile a script spawns or a sound it plays on an event, add it to Script Assets:

  1. Choose Tools → Mantle → Place settings. This selects the level's Mantle Place Settings actor, and adds one if the level has none.
  2. In the Details panel, under Mantle → Scripts, add entries to Script Assets and pick each asset. It takes static meshes, materials and sound waves.
  3. Publish. Script Assets are checked and uploaded exactly like placed content, with the same limits.
  4. Find each asset's id in the publish log, one line per asset: Script asset /Game/Props/SM_Boulder.SM_Boulder = ast_u…. The same ids show in the read-only Script Asset Ids list until you reopen the level or close the editor. Use that id in your script. Test Locally gives each asset a different id, shown only in the Mantle Preview panel and in the editor log as MANTLE_PREVIEW_EXPORT script asset <path> = <id>, so a script that spells an id out needs the published id after you publish.

A mesh brings its slot materials with it. An asset that's also placed in the level, or listed twice, is published once. Check this place names anything the list can't publish, such as a texture, a Sound Cue or MetaSound, or a deleted asset, and Publish refuses the same entries.

Lights (API 1.7)

Every point, spot and directional light in the place is an Entity with LightEnabled, LightColor ("#RRGGBB"), LightIntensity, LightRange and, for spot lights, LightInnerCone/LightOuterCone. LightKind says which kind it is, or nil for anything that isn't a light. Set them on the server and every player sees the change, including players who join later; set them on a client and only that player does. Lights:Spawn Server adds a new light. Shadows are off unless you pass CastShadow = true. A place can have at most 64 spawned lights at once; lights you placed in the editor don't count.

Spawning and recoloring meshes (API 1.8)

Assets:Spawn(assetId, position, props?) Server places one of the place's meshes (placed in the level or listed under Script Assets) and returns it as an Entity. Spawned meshes count toward the same 512 limit as clones. Any mesh can be tinted with Color, faded with Transparency (0 solid to 1 invisible), or given another of the place's materials with SetMaterial(assetId, slot?). Only materials uploaded with the place can be tinted or made see-through. A spawned mesh stays where a script puts it: it can't be a physics object.

Physics objects (API 1.15)

A static mesh with Simulate Physics turned on in the editor is published as a physics object: the server simulates it and every player sees it move. A player who joins later sees each one where the server has it, so a prop that has come to rest, or hangs from a rope, stays put for them too. On the server, ApplyImpulse and ApplyAngularImpulse push and spin it, Velocity reads or replaces its speed in cm/s, Anchored = true pins it in place and false lets it fall, and Mass reads its mass in kg. Collided(other) fires on the server when it starts touching something: another entity, a player's character, or nil. Every other entity is always anchored, and physics objects can't be cloned yet. A place can hold 500 physics objects.

Scripts/Server/Crate.luau
local crate = World:FindFirst("PhysicsCrate")
crate.Collided:Connect(function(other)
	print("hit", other and other.Name or "the world")
end)
-- Launch it upwards: an impulse in kg·cm/s, so divide by Mass for the speed change.
crate:ApplyImpulse(Vector3.new(0, 0, 800) * crate.Mass)
Scripts/Server/Crate.ts
const crate = World.findFirst("PhysicsCrate")!;
crate.collided.connect((other) => {
	console.log("hit", other ? other.name : "the world");
});

crate.applyImpulse(new Vector3(0, 0, 800).mul(crate.mass));

Joints: welds, hinges and ropes (API 1.30)

A Physics Constraint Actor between two physics objects (or one and the world) publishes as a Constraint: a weld (no movement between them), a hinge (one turns about an axis, within limits) or a rope (the anchors stay within a length of each other). Constraints:Create(params) Server makes one at runtime and returns it; Constraints:FromEntity(entity) finds the joint a place's own Constraint made. Pull a joint harder than its BreakForce (newtons) and it breaks for good: Broken fires once, on the server. The two joined entities stop colliding with each other, and a place holds at most 200 joints, its own included. Joints exist only on the server: players just see the entities move.

Scripts/Server/Door.luau
local door = World:FindFirst("Door")
local hinge = Constraints:Create({
	Type = "hinge", EntityA = door, AnchorA = Vector3.new(0, -50, 0),
	Axis = Vector3.new(0, 0, 1), Limits = { -90, 0 }, BreakForce = 20000,
})
hinge.Broken:Connect(function() print("the door came off") end)
Scripts/Server/Door.ts

Raycasts and area queries (API 1.6)

World:Raycast(origin, direction, params?) returns the first thing a ray hits as a table of Entity, Player (set when it hit a character), Position, Normal and Distance, or nil. Spherecast and Blockcast sweep a ball or box the same way, and GetEntitiesInRadius and GetEntitiesInBox list everything inside a shape, nearest first. params takes MaxDistance, Include, Exclude, Tag and IgnorePlayers. Queries run on the machine that asks, work on both sides, and reach at most 1 km. A ball can have a radius of up to 50 m and a box can be up to 100 m on a side. A list holds at most 256 entities, and a script can make 256 queries a frame. Rays pass through trigger (overlap-only) entities and never hit entities with no collision.

Scripts/Server/Laser.luau
local laser = World:FindFirst("Laser")
while true do
	local hit = World:Raycast(laser.Position, Vector3.new(1, 0, 0), { MaxDistance = 3000, Exclude = { laser } })
	if hit and hit.Player then
		hit.Player:TakeDamage(10)   -- API 1.9
	end
	task.wait(0.25)
end
Scripts/Server/Laser.ts
const laser = World.findFirst("Laser")!;
task.spawn(async () => {

		const hit = World.raycast(laser.position, new Vector3(1, 0, 0), { maxDistance: 3000, exclude: [laser] });
		if (hit && hit.player) {
			hit.player.takeDamage(10);   // API 1.9
		}

Time of day and weather (API 1.4 and 1.11)

Every server has one sky, shared by every player. Environment.TimeOfDay runs from 0 to 24 (servers start at 9, and a day lasts 30 real minutes), IsNight is true while the sun is down, and Weather is Clear, PartlyCloudy, Overcast, Rain, Storm, Cloudy, Foggy, LightRain, LightSnow, Snow, Blizzard, DustCalm or DustStorm. NPCs (API 1.17)

NPCs:Spawn(position, look?, yaw?) Server adds a character that the server walks and animates, and every player sees. look takes AvatarItemId (the item id of a published avatar body, such as the one Player.Avatar reads; without it the NPC has no body to draw), SkinTone and EyeColor (avatar palette ids such as "tone_05") and Height (a percent from 95 to 105; values outside are clamped). Only cars and trucks work, and the vehicle must have no driver. MoveTo returns false at once for a target more than 500 m away or a dead NPC. From API 1.42, Follow walks an NPC after a player, an entity or another NPC, and Attack makes one its enemy. See Explosions, projectiles and NPC attacks.

Script packages and Script Points (API 1.35)

A script package is a set of scripts a place stores from the library, or keeps in a Packages/<Name>/ folder beside Scripts/ while you build it. Its Server/ and Client/ scripts start like the place's own, once on each side, and its Shared/ and Modules folders only hold modules. Its scripts have the same abilities and limits as any other script on their side.

  • Script.Package is the name the place's storage gives the package this script belongs to, such as "Hazards", or "" in one of the place's own scripts.
  • Script.Points lists the enabled Script Points placed for this package. Each is an Entity at the point's position and rotation, tagged with the package's storage name. Its parameters are attributes: point:GetAttribute("Radius"). Numbers and true/false arrive converted, as the package's package.json declares them, and a parameter a point leaves out takes the package's default. A place script gets an empty list.
  • Script.Settings (API 1.36) holds the package-wide settings the place chose in Place Settings → Storage, by name, typed the same way (a choice is its text). A setting the place leaves unset has the package's default, and one with neither is nil: Script.Settings.RoundLength. A place script gets an empty table.
  • Storage:Get(name) (API 1.34) also answers a stored package's library item id.

A package's scripts run once per side however many points there are, so loop over the points rather than expecting one script per point:

Collision layers (API 1.43)

A collision layer is a named group of objects. Private chat and voice (API 1.44)

A server script can narrow who sees a chat line or hears a voice. Chat:SendToPlayers(players, text) Server posts a line from the place to up to 10 players. Chat:SetAudience(player, recipients?) turns what a player types into a team channel for up to 128 players. For voice, Voice:SetMuted silences a player for everyone, Voice:MuteFor does it for one listener and Voice:SetAudience makes a speaker heard only by a list of players. Voice:CanHear, IsMuted and IsSpeaking read the state, and Voice:Reset clears the rules.

A private line is private to its players, not hidden from Mantle:

  • Filtered: the same chat filter checks every line. A place's private lines count toward the same 10 lines a minute per server as Chat:SendSystemMessage.
  • Blockable and reportable: a player's own blocks still hide what other players write, and every line can be reported. Whispers are also rate-limited.
  • Seen by Mantle's moderators: Mantle keeps every line, private ones too, and its moderation tools can still read them.
  • Not read by scripts: a place's scripts can't read private lines back. Chat.MessagePosted never fires for a whisper.
  • Only ever quieter: your rules can only show a line to fewer people or silence a voice, never the reverse. A player who has muted or blocked someone keeps them muted whatever your script does.

Voice goes straight between players' games, not through the server, so the server can't hear or record it, and each listener's game applies the mute. Swimming and breath (API 1.45)

Characters swim in a place's water bodies: lakes, rivers, oceans and custom bodies. A character starts swimming when the water reaches about its chest, and stands up again when the water is shallow enough to walk in. Wading in shallow water isn't swimming.

  • Moving: move to swim at the surface. Hold sprint for a faster stroke. Walk slowly (the walk key, or push the stick lightly) to tread water: you face the camera and drift any way. Crouch dives, and jump rises. Next to a ledge at the surface, jump climbs out.
  • Currents: a river's current carries a swimmer. A current slower than the swimmer's stroke can be beaten. A stronger one can't.
  • Speed: with the default WalkSpeed a swimmer moves at 260 cm/s, 520 cm/s with the sprint stroke and 130 cm/s while treading. WalkSpeed scales all three, and SprintSpeed scales the sprint stroke. WalkSpeed = 0 stops a swimmer. A script's crouch settings don't stop the dive.
  • What doesn't work in water: aiming and guarding. A tool can be held but not used. An emote ends when the swim starts. Vaulting and climbing don't start from a swim.
  • Dying: a character that dies in water doesn't ragdoll. It plays a dying animation and floats where it died.
  • Reading it: IsSwimming is true while the character swims. IsUnderwater is true while it swims with its head under the surface. Both can be read on the server and on every client.

Breath is off until a server script sets BreathEnabled = true, so swimming is free in places that never use it. Turning it on starts the breath full. Breath counts seconds of air: it drops by one a second while IsUnderwater. With the head out of the water, it waits BreathRegenDelay seconds and then refills at BreathRegen seconds a second. When it reaches 0, OutOfBreath fires, and the character loses DrownDamage health every second it stays under. That damage skips Armor and Shield, has no killer and has the damage type "Drown", so a drowning death fires Player.Died with "Drown" and a nil killer.

SettingDefaultAllowed values
MaxBreath20 seconds1 to 3,600
BreathRegen10 seconds a second0 to 10,000
BreathRegenDelay0.5 seconds0 to 60
DrownDamage10 health a second (dealt once a second)0 to 10,000. 0 means a character never drowns.

Only the server can set BreathEnabled, Breath and these settings, and every machine can read them. A number outside the range is clamped to it. The settings last for the rest of the session, through respawns, and every new character starts with full breath. Setting Breath clamps it to 0 to MaxBreath and restarts the wait before it refills. Lowering MaxBreath below Breath lowers Breath too, and a full breath stays full when you raise it. The signals BreathChanged(player, old, new), OutOfBreath(player) and BreathRestored(player) fire on the server and on every client. BreathChanged passes the old value, then the new one, in steps of about half a percent of MaxBreath, and only while BreathEnabled is true. Mantle has no built-in breath bar: see the breath recipe for one, and Player for every member.

Calling web services (API 1.46)

A server script can call a web service: your own backend, a Discord webhook or any public data API. Http:RequestAsync(options) Server sends the request. Players' games never make these requests. Http:IsAvailable() Server is false when the server's operator turned outbound requests off, so a place can quietly do without them.

RequestAsync returns a signal that fires once with the result. Call Wait() on it right away (see Waiting and timers). The result has ok (true only for a 2xx answer), status, headers, body, url, error and code. A 404 or 500 still comes back with its status and body, and code is "http_status". A request that failed after it was sent has ok = false and a code such as "dns_failed", "timeout" or "response_too_large".

In Python, wait() only works inside a generator, and the result comes back in a tuple: token = Http.request_async({...}).wait(), then yield token, then result = token.result[0].

local result = Http:RequestAsync({ url = "https://example.com/api/status" }):Wait()
if result.ok then
	local data = Http:JsonDecode(result.body)
	print(data.message)
else
	warn(`request failed: {result.code}`)
end

Http:JsonEncode(value) turns a value into JSON text, and Http:JsonDecode(text) turns JSON text into a value (objects become tables with string keys, arrays become lists and null becomes nil). Both work on the server and on clients, and both raise an error for something that isn't valid JSON. JavaScript and Python have their own JSON and json. Luau has none, so these are mostly for Luau.

An address must start with http:// or https:// and use port 80, 443 or 1024 and up. Private and internal addresses are always refused. A body can be up to 2 MiB (not with GET) and a response up to 8 MiB. A timeout is 1 to 60 seconds (30 by default), and up to 5 redirects are followed. A server can have 16 requests under way at once, with 128 more waiting, and about 600 a minute. A request that's refused before it's sent raises an error that starts with a code, such as bad_url, blocked_address, blocked_port, body_too_large, rate_limited or disabled. Catch it with pcall (Luau) or try (JavaScript, TypeScript and Python). See Http for every member.

Mantle logs the host, port, status and size of each request, never its path, headers or body. It also keeps a per-minute summary for each script and host (how many requests, how they ended and how many bytes) for 180 days, so moderators can look into abuse. Don't put a key in a script: store it as a secret.

Secrets (API 1.47)

A secret is a named value, such as an API key or a webhook address, that you store for your place instead of writing it in a script. Secrets:Get(name) Server returns the value, or nil when the place has no secret by that name. Secrets:IsAvailable() Server says whether this server loaded the place's secrets at all. Check it first, so a place can say what's missing instead of failing quietly.

  • Names: upper-case letters, digits and underscores, starting with a letter, up to 64 characters, like DISCORD_WEBHOOK. Any other name is an error.
  • Limits: 50 secrets for a place, and up to 8 KiB for each value.
  • Where they work: server scripts on a Mantle-hosted dedicated server only. Community servers don't get secrets, and neither does standalone or listen play of a published place. There, IsAvailable is false and Get returns nil for every name. It's also false when the server couldn't reach Mantle to load them.
  • When they load: before any script starts, so the value is there from your script's first line. A change reaches servers that start after it. A server that's already running keeps the values it loaded.
  • Setting them: in the editor, under Place settings. See Secrets for creators, including how to test with a secrets.local.json file.

Never send a secret to a player

Anything a client gets, its player can read. Don't pass a secret's value in a remote event, State, an attribute, chat or UI. Use it to call a service from the server. Until secrets work everywhere, use keys you can rotate, and never put a long-lived key in a script.

The avatar editor (API 1.48)

A client script can open Mantle's avatar editor over the running place, so a player changes their own look while the world goes on behind it: a barber chair that only changes hair, or a wardrobe that only changes clothes. Avatar:OpenEditor(options?) Client opens it and returns true. It returns false, and opens nothing, when the player has no character or the editor or another Mantle screen is already open. The player sees only items they own or that are free, and Save puts the look on their account just like Mantle's own avatar screen. Esc, the gamepad's B and the Close button shut it, asking first about unsaved changes.

  • Categories: a list that limits what the editor offers: "body", "hair", "clothes", "accessories", "emotes" or "all", or slot names such as "top" or "acc_hat". Leave it out to offer everything: only then are outfits offered too. An unknown name is a script error.
  • Title: a heading over the panel, up to 40 characters.
  • FreezeCharacter: true by default, which holds the character still and turns the camera onto it. False leaves the player in control and the camera where it is.

Avatar:CloseEditor() Client closes it like the Close button, without asking: unsaved changes are put back. It returns false when the editor wasn't open. Avatar:IsEditorOpen() Client says whether it's open, whoever opened it. The signals EditorOpened() and EditorClosed(saved) fire when it opens and closes, and saved is true when the player saved a look while it was open. LookChanged(slot, oldItem, newItem) fires once for each slot whose item changed, when the player's account confirms a save (from this editor or from Mantle's own avatar screen). The slot is "avatar" or a slot name such as "hair", "top" or "acc_hat", and the items are item ids, nil for nothing worn there. All of these are client only: a server script that calls them gets the usual error. See the barber recipe, and Avatar for every member.
