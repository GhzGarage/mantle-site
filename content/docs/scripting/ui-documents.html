UI documents need script API 1.31 and the game release that brings it. Until then, a place whose scripts use UI documents can't be published, because its scripts need a newer script API than the released game. Details on this page may change before then.

What UI documents are

A UI document is a screen of your world's interface written as markup and styles, like a small web page: a shop, a menu, a scoreboard, a quest log or a HUD panel. You write it in two kinds of plain text file:

  • .rml files hold the markup. RML reads like HTML: <div>, <p>, <h1>, <button>, <img> and so on.
  • .rcss files hold the styles. RCSS reads like CSS, with flexbox, transitions, animations and transforms, and a few differences listed under Styling.

They go in a UI/ folder next to your level's Scripts/ folder. A client script opens a document with UI:OpenDocument, gives it values to show with SetData, and hears the player's clicks through its Event signal. Documents contain no code of their own: all the logic stays in your scripts.

UI documents publish the same way scripts do. Publish uploads them with your scripts, Mantle screens them, and they go live with the revision. Nothing is cooked or packaged, so publishing a changed document takes seconds.

Documents are drawn by RmlUi 6.3, an open-source (MIT) HTML/CSS-like interface library, through the game's own UI. RmlUi's documentation is a good reference for RML elements and RCSS properties. Where Mantle differs, this page wins.

UI documents or UI nodes?

Mantle already has a simpler way to put UI on screen from a script: UI:Create(kind) builds UI nodes (frames, text, images, buttons, toggles, lists, grids, scroll areas and prompts) one at a time from code (see the UI reference). Both work in the same place, and you can use both at once.

UseWhen
UI:Toast, UI:SetTextA quick message or a single line of HUD text.
UI nodes (UI:Create)A few widgets you build and change from code: a label, a button, a prompt. Up to 256 nodes per script.
UI documents (UI:OpenDocument)A designed screen with real layout and styling: shops, inventories, menus, dialogue, scoreboards, styled HUD panels. You describe it once in markup, and it redraws itself when your script changes its data. Documents also handle mouse, keyboard and gamepad input, and closing with Back, for you.

Your first document

This builds a welcome panel that shows how many players are in the world and closes when the player presses Play.

  1. Make a UI folder beside Scripts

    If your level is Content/MyPlace/MyPlace.umap, its scripts are in Content/MyPlace/Scripts/ and its documents go in Content/MyPlace/UI/.

  2. Add the document
    UI/welcome.rml
    <rml>
<head>
	<title>Welcome</title>
	<link type="text/rcss" href="welcome.rcss"/>
</head>
<body>
	<div class="card">
		<h1>Welcome!</h1>
		<p>{{online}} players are here.</p>
		<button data-event-click="emit('play')">Play</button>
	</div>
</body>
</rml>

    {{online}} shows a value your script sets. data-event-click="emit('play')" tells your script the button was clicked.

  3. Add a stylesheet
    UI/welcome.rcss
    body { display: flex; justify-content: center; align-items: center; }

.card {
	width: 420dp;
	padding: 24dp;
	border-radius: 14dp;
	background-color: #191919E6;
	border: 1dp #444443;
}

    You don't need to style the heading, the text or the button: Mantle's base stylesheet already gives them sizes, colours, a focus ring and keyboard and gamepad navigation.

  4. Open it from a client script
    Scripts/Client/Welcome.luau
    local welcome = UI:OpenDocument("UI/welcome.rml")
welcome:SetData("online", #Players:GetPlayers())

welcome.Event:Connect(function(name, args)
	if name == "play" then
		welcome:Close()
	end
end)
    Scripts/Client/Welcome.ts
    const welcome = UI.openDocument("UI/welcome.rml");
welcome.setData("online", Players.getPlayers().length);

welcome.event.connect((name: string, args: any[]) => {
	if (name === "play") {
		welcome.close();
	}
});
    Scripts/Client/Welcome.js
    const welcome = UI.openDocument("UI/welcome.rml");
welcome.setData("online", Players.getPlayers().length);

welcome.event.connect((name, args) => {
	if (name === "play") {
		welcome.close();
	}
});
    Scripts/Client/Welcome.py
    welcome = UI.open_document("UI/welcome.rml")
welcome.set_data("online", len(Players.get_players()))

def on_event(name, args):
    if name == "play":
        welcome.close()

welcome.event.connect(on_event)

    With no mode given, the document opens as a modal: the player's character stops taking input, the cursor appears, the Play button has focus, and Esc or the gamepad's B button closes the panel too.

  5. Check, publish and join

    Run Check All in the Scripts panel for your script and Check this place for the document, then publish with Mantle → Publish and join in the Mantle client. Check this place loads every document the way players' games do, so a broken link or a typo in the markup shows up in the editor (see Limits and checks).

    In development builds you can skip publishing: a server or client started with -MantlePlace=<path>/place.json reads the UI/ folder beside that file. It reads the folder once, when the world loads, so restart the client after you edit a document. Script hot reload doesn't re-read UI files.

Files and folders

A level with UI documents

  • Only .rml, .rcss, .png and .jpg files are published from UI/. Extensions must be lower case; .jpeg is refused. Other image types (SVG, GIF, WebP and the rest) in UI/ aren't published, and Check warns about them.
  • File and folder names can use only letters, digits, _, . and -. A path, starting at UI/, can be up to 200 characters. Two paths that differ only in capital letters aren't allowed.
  • Each .rml or .rcss file can be up to 256 KiB, and a place can have up to 64 of them. Images have their own count and size limit; see Images.
  • A .rml or .rcss file inside Scripts/ is an error. Check tells you to move it to UI/.

You open a document by its path from the level folder, exactly as spelled: UI:OpenDocument("UI/hud/coins.rml"). Paths are case-sensitive. If only the case is wrong, the error tells you the right spelling. You can only open .rml files; stylesheets are linked from documents.

Inside a document, links are relative to the document's own folder: <link type="text/rcss" href="shop.rcss"/> next to it, href="../common.rcss" one folder up, or href="/UI/common.rcss" from the top. A document can link any .rcss file and any RmlUi template (an .rml file) in your place's UI/ folder, and nothing else: web addresses, drive paths and anything above UI/ are refused. A document can also hold styles inline in a <style> element in its <head>.

RML is stricter than HTML: every element needs a closing tag or a self-closing />, attribute values need quotes, and the whole file sits inside <rml> with a <head> and a <body>.

The script API

Everything is Client only: calling it from a server script is an error. Names are shown in Luau. In JavaScript and TypeScript they're UI.openDocument, setData, setMode, close, isOpen, event and closed. In Python they're UI.open_document, set_data, set_mode, close, is_open, event and closed.

MemberWhat it does
UI:OpenDocument(path, mode?) → UiDocumentOpen one of your place's documents on this player's screen. mode is "modal" (the default), "overlay" or "hud" (see Modes and input). An unknown path or mode is an error. A script can have up to 16 documents open at once. The call returns straight away and the document appears on the next frame; values you set in the meantime are there for its first frame.
doc:SetData(key, value)Give the document a value to show (see Data binding). Does nothing once the document has closed.
doc:SetMode(mode)Switch between "modal", "overlay" and "hud" while it's open. Does nothing once it has closed.
doc:Close()Close it. Closing twice is fine, and Closed doesn't fire for your own Close.
doc.IsOpenTrue until the document closes, for whatever reason.
doc.Event(name, args)Signal. The document called emit(name, ...). args is a list of the other values it passed (see Events).
doc.Closed(reason)Signal. The document closed by itself: the player pressed Back, or it failed to load or went over a limit (see Closed reasons).

A document belongs to the script that opened it. Only that script can change or close it, and it closes when that script stops, including on a hot reload. When the place unloads, documents close along with your scripts.

A few things decide whether a document takes input at all:

  • It needs something to focus. A modal or overlay document only takes input when it has at least one visible focusable element. The base stylesheet makes <button>, <input>, <textarea> and <select> focusable. To make any other element a control, give it tab-index: auto; nav: auto; in RCSS. nav: auto lets the arrow keys, D-pad and stick move to it. A document with nothing focusable is drawn but takes no input, like a HUD.
  • It waits its turn. If something else already shows the cursor, such as the game menu or a script's interactive UI nodes, the document waits and takes input once that lets go. When the document closes, the player's input goes back exactly as it was.
  • The script chooses the mode. The mode you pass to OpenDocument or SetMode is the one that counts.

Back always closes a modal document, and your script hears it as Closed("back"). If you want to react to that, for example to reopen a shop later or unpause a timer, connect to Closed.

Data binding

Your script owns the data; the document shows it. Call SetData(key, value) with a number, string, boolean, Vector3, list or table (object in JavaScript, dict in Python), and every part of the document that uses that key redraws by itself. Nothing else is touched, so setting one value is cheap.

In the documentWhat it doesExample
{{ expression }}Shows a value in text.{{coins}} coins, {{stats.kills}}, {{items.size}} items
data-forRepeats the element once for each item of a list. Add a second name for the position, counted from 0.data-for="item : items", data-for="item, i : items"
data-ifShows the element only while the expression is true. Otherwise it's hidden and takes up no room.data-if="coins >= 100"
data-visibleLike data-if, but a hidden element keeps its space.data-visible="!loading"
data-class-nameAdds the class name while the expression is true.data-class-owned="item.owned"
data-style-propertySets one style property from a value.data-style-width="health + '%'"
data-attr-nameSets an attribute from a value.data-attr-src="icon", data-attr-mantle-label="coins + ' coins'"
data-attrif-nameAdds the attribute while the expression is true.data-attrif-checked="musicOn"
data-value, data-checkedTies a text field's text, or a checkbox, to a key in both directions (see Forms).<input type="text" data-value="nickname"/>
data-event-eventRuns an expression when the event happens, usually emit(...) (see Events).data-event-click="emit('buy', item.id)"

Expressions can use arithmetic, comparisons, &&, ||, !, the a ? b : c choice, and + to join text. After a | you can apply format(digits), round, to_upper or to_lower: {{ speed | format(1) }} m/s. Whole numbers show without decimals. A Vector3's parts are .x, .y and .z, in lower case.

A key the script hasn't set yet shows as empty, so a document can open before its data arrives. Some rules for keys and values:

  • A key starts with a letter and uses only letters, digits and _, up to 64 characters. Keys are case-sensitive. it, it_index, ev, true, false, size and literal are taken.
  • A document holds up to 256 keys.
  • A value can be up to 64 KiB once encoded and nested up to 16 levels. It can't hold functions, entities or players (send the fields you need, such as player.Name), or NaN or infinity. A value that breaks these rules is an error in your script.
  • Use lists for anything you repeat with data-for. A table with named keys repeats its values in an order you can't count on.
  • The document gets a copy. Changing your table afterwards changes nothing on screen until you call SetData again.

Mantle connects the document to your script's data automatically. Leave out RmlUi's data-model attribute: a <body> that names a different data model gets no script data, and Check warns about it.

UI/quests.rml (body only)
<body>
	<div class="quests">
		<h2>Quests ({{quests.size}})</h2>

			<div class="title">{{quest.title}}</div>
			<div class="bar"><div class="fill" data-style-width="(quest.progress * 100) + '%'"></div></div>

Events: from the document to your script

A document tells your script something happened by calling emit(name, ...) in a data-event-* attribute. The first value is the event's name; the rest arrive in args, in order. Your script's Event handler runs on the next frame.

In the document
<button data-event-click="emit('buy', item.id, item.price)">Buy</button>
<div class="tab" data-event-mouseover="emit('hover', 'gear')">Gear</div>
In a client script
shop.Event:Connect(function(name, args)
	if name == "buy" then
		local itemId, price = args[1], args[2]
		-- ...
	end
end)
In a client script
shop.event.connect((name: string, args: any[]) => {
	if (name === "buy") {
		const [itemId, price] = args;
		// ...
	}
});
In a client script
shop.event.connect((name, args) => {
	if (name === "buy") {
		const [itemId, price] = args;
		// ...
	}
});
In a client script
def on_event(name, args):
    if name == "buy":
        item_id, price = args[0], args[1]
        # ...

shop.event.connect(on_event)

Numbers, text and booleans arrive as they are. Anything else, such as a colour, arrives as text. Across all open documents, up to 256 events are delivered per frame; more than that in one frame are dropped, with a warning in the log.

Any event RmlUi raises can trigger data-event-*: click, dblclick, mouseover, mouseout, focus, blur, change, submit, keydown and others. In the expression, ev holds the event's details, such as ev.value in a change event.

An event expression can also set one of the document's own values, for UI state your script doesn't care about, such as which tab is showing: data-event-click="tab = 'gear'" with data-if="tab == 'gear'" on the tab's content. Set the key's starting value with SetData first. The next SetData for that key replaces what the document set.

Forms

data-value keeps a text field's text in one of the document's values. Your script doesn't see it until the document sends it:

UI/rename.rml (body only)
<body>
	<div class="card">
		<input type="text" data-value="nickname"/>
		<button data-event-click="emit('rename', nickname)">Save</button>
	</div>
</body>

Call SetData("nickname", "") (or the current name) when you open it, so the field has a value to write to.

reasonWhy it closed

Buying things: check on the server

A document runs on the player's machine, and so does the client script that hears its events. Treat an event like any other message from a player: fine for choosing a tab, never enough on its own to give out coins or items. Send the request to the server with a remote, check it there, and send the result back for the document to show. Shown in Luau; the other languages work the same way.

Scripts/Server/ShopServer.luau
local PRICES = { ember_cape = 120, spark_trail = 80 }
local buy = Net:Remote("ShopBuy")
local coins = Net:Remote("ShopCoins")
local wallet = {}

Players:OnPlayer(function(player)
	wallet[player] = 500
	coins:FireClient(player, wallet[player])
end)

Players.PlayerRemoving:Connect(function(player)
	wallet[player] = nil
end)

buy.OnServerEvent:Connect(function(player, itemId)
	local price = PRICES[itemId]
	if price == nil or wallet[player] == nil or wallet[player] < price then
		return
	end
	wallet[player] -= price
	coins:FireClient(player, wallet[player])
end)
Scripts/Client/Shop.luau
local shop = UI:OpenDocument("UI/shop.rml")
shop:SetData("items", {
	{ id = "ember_cape", name = "Ember Cape", price = 120 },
	{ id = "spark_trail", name = "Spark Trail", price = 80 },
})

Net:Remote("ShopCoins").OnClientEvent:Connect(function(amount)
	shop:SetData("coins", amount)
end)

shop.Event:Connect(function(name, args)
	if name == "buy" then
		Net:Remote("ShopBuy"):FireServer(args[1])
	end
end)

Styling

RCSS is close to CSS: selectors (classes, ids, descendants, :hover, :active, :focus, :focus-visible, :checked, :nth-child and more), the box model, box-sizing, block, inline, inline-block, flexbox, tables, position: absolute | relative | fixed, z-index, overflow, opacity, transform, border-radius, transitions and @keyframes all work. The differences that catch people out:

  • Use dp for sizes. dp follows the player's screen and UI scale, so a panel is the same size on a 1080p and a 4K screen. px is a physical pixel. %, em, rem, vw and vh work as in CSS.
  • No browser defaults. RmlUi starts every element as display: inline with no margins. Mantle's base stylesheet fills in the common cases; anything it doesn't cover (h4, ol, table elements) needs your own rules.
  • No CSS grid. Use flexbox (flex-wrap: wrap gives you grids of tiles) or tables.
  • Borders are always solid and the shorthand takes a width and a colour: border: 1dp #444443. There's no solid/dashed keyword.
  • Backgrounds are a colour, a gradient or an image. background-color works. A two-colour blend is a decorator: decorator: horizontal-gradient(#EB6036 #FFAE28) or vertical-gradient(...); for more stops, an angle or a radial or conic sweep, linear-gradient(...), radial-gradient(...) and conic-gradient(...) draw too (and their repeating- forms), up to 16 colour stops. For a picture, use <img> or decorator: image(...) with a file from your place's UI/ folder (see Images).
  • box-shadow draws, outer and inset, with blur, spread and rounded corners. A shadow with no offset and no spread is a glow that shows through the element's own background, as CSS specifies.
  • Text shadows and outlines are font effects: font-effect: shadow(2dp 2dp #000000AA) or font-effect: outline(1dp #000000).
  • Colours can be names, #RGB, #RRGGBB, #RRGGBBAA (with alpha), rgb(), rgba(), hsl() and hsla().
  • Cursors: cursor: pointer shows a hand and default the normal arrow. Other cursor names aren't supported.
  • Scroll areas (overflow: auto or scroll) scroll with the mouse wheel, but RmlUi draws no scrollbar until you style one (its scrollbarvertical, slidertrack and sliderbar elements).
What still doesn't draw

Mantle draws documents through the game's own UI renderer, which doesn't yet support RmlUi's layer effects: filter, backdrop-filter (so no blur-behind) and mask-image. A document that uses one of these still loads, and the element still draws, just without that effect. Check this place and Publish warn about each one, and the client log adds one line the first time a document that uses them loads. overflow: hidden still clips to the element's rectangle, even when it has rounded corners.

Fonts and languages

Documents use Mantle's built-in fonts. You can't load your own, and @font-face is refused.

  • Roboto: regular, medium (font-weight: 500) and bold. The default.
  • "Roboto Condensed": bold only.
  • "Noto Naskh Arabic UI": Arabic. For joined, right-to-left Arabic, put lang="ar" on the element and give it font-family: "Noto Naskh Arabic UI". Arabic in a Roboto element still draws, but as separate, unjoined letters.

There's no italic face, so font-style: italic draws upright text. Text in scripts these fonts don't cover, such as Chinese, Japanese or Korean, doesn't draw.

Mixed-direction text lays out correctly: an Arabic or Hebrew phrase inside an English sentence, or an English word inside one of those, is split, shaped and ordered by the Unicode bidi algorithm rather than drawn strictly left to right, so it reads the way it would in any other app. This is automatic, nothing to opt into. Caret placement and text selection inside an <input> or <textarea> holding mixed-direction text are a known gap.

Images

Put PNG or JPEG files anywhere under your place's UI/ folder, such as UI/icons/sword.png, and reference them by a path relative to the file that uses them, the same way a stylesheet links another file:

Animations and transitions

Transitions and @keyframes animations work as in CSS, with RmlUi's own names for the easing curves: linear, sine, quadratic, cubic, quartic, quintic, exponential, circular, back, elastic and bounce, each with -in, -out or -in-out. CSS names such as ease-in-out and cubic-bezier() don't exist.

UI/hud.rcss
button { transition: background-color 0.15s cubic-out; }

.toast { animation: 0.4s back-out pop; }
@keyframes pop {
	from { transform: translate(0dp, 20dp) scale(0.8); opacity: 0; }
	to   { transform: translate(0dp, 0dp) scale(1); opacity: 1; }
}

.pulse { animation: 1.2s sine-in-out infinite alternate glow; }
@keyframes glow {
	from { opacity: 0.6; }
	to   { opacity: 1; }
}

Animate transform and opacity whenever you can. They move and fade what's already laid out. Animating width, height, margins or top/left makes RmlUi lay the document out again every frame (see Performance).

Respect players who asked for less motion: send UI.ReducedMotion to the document and turn animations off with a class.

Document and stylesheet
<body data-class-calm="calm"> ... </body>

.calm .pulse { animation: none; }
Client script
hud:SetData("calm", UI.ReducedMotion)

Accessibility

Screen readers only see the elements you label. Three attributes describe an element:

AttributeWhat it does
mantle-labelWhat the screen reader says for the element. Without it, the element is invisible to screen readers.
mantle-hintRead after the label: "Buy Ember Cape. 120 coins".
mantle-rolebutton, toggle, text, image or heading, in lower case. Without it, a focusable element is a button and anything else is text. A heading is read as text. A toggle reads as checked while the element has the checked attribute.

The screen reader follows focus as the player moves with the keyboard or gamepad, and activating a labelled button or toggle from the screen reader clicks it. Use data-attr-mantle-label and data-attr-mantle-hint for labels that change, as in the shop above. Also consider UI.TextScale, UI.HighContrast and UI.ReducedMotion: send them with SetData and adapt with data-class-* or data-style-*.

Performance

A typical HUD of a few hundred elements costs about 0.3 ms a frame. Documents get expensive when thousands of elements change every frame: thousands of elements animating at once cost several milliseconds, which players feel as a lower frame rate. To stay fast:

  • Keep element counts modest. Show the 20 visible rows of a long list, not all 2,000.
  • Animate transform and opacity. Animating sizes, margins or positions re-lays out the document every frame. A few animated health bars are fine; hundreds of them at once are not.
  • Split fast-changing values into their own keys. SetData only redraws what uses that key, so a timer in SetData("time", t) is cheap, while resending a large table ten times a second copies and redraws all of it.
  • Don't update faster than players can read. A counter that changes 20 times a second rebuilds its text 20 times a second.
  • Close what isn't showing. Open a document when the player needs it and close it afterwards, rather than keeping a screenful of hidden panels open.

In development builds, the console command Mantle.Rml.LogFrameCost 1 logs every document's update and draw cost, element count and the game's frame time every 5 seconds.

Worked example: a drag-and-drop inventory grid

A grid of slots the player drags items between, with the picked-up item's icon following the cursor. One document, one stylesheet, one client script.

UI/inventory.rml
<rml>
<head>
	<title>Backpack</title>
	<link type="text/rcss" href="inventory.rcss"/>
</head>
<body>
	<div class="panel">
		<h2 mantle-role="heading">Backpack</h2>
		<div class="grid">
			<button class="slot" data-for="s, i : slots"
				data-class-empty="s.empty"
				data-event-dragdrop="emit('drop', i)"
				data-attr-mantle-label="s.empty ? 'Empty slot' : s.name + ', ' + s.count">
				<div class="item" data-if="!s.empty" data-event-dragstart="emit('pick', i)">
					<img class="icon" data-attr-src="s.icon"/>
					<div class="count" data-if="s.count > 1">{{s.count}}</div>
				</div>
			</button>
		</div>
	</div>
</body>
</rml>
UI/inventory.rcss
.panel { position: absolute; left: 50%; top: 50%; width: 460dp; margin-left: -230dp; margin-top: -230dp;
	padding: 18dp 20dp; background-color: #191919F0; border: 1dp #444443; border-radius: 14dp; }
.grid { display: flex; flex-wrap: wrap; width: 420dp; margin-top: 12dp; }
.slot { width: 88dp; height: 88dp; margin: 6dp; padding: 0dp; border-radius: 10dp; background-color: #272726; border: 2dp #444443; }
.slot:hover { border-color: #A19E98; }
.item { position: relative; width: 84dp; height: 84dp; drag: clone; }
.icon { position: absolute; left: 10dp; top: 10dp; width: 64dp; height: 64dp; }
.count { position: absolute; right: 6dp; bottom: 2dp; font-weight: bold; color: #FFFFFF; }
Scripts/Client/Inventory.luau
local SLOTS = 12
local slots = { -- index -> { id, count }; a gap is an empty slot
	{ id = "sword", count = 1 },
	nil,
	{ id = "potion", count = 3 },
}
local ITEMS = {
	sword = { name = "Ember Sword", icon = "icons/sword.png" },
	potion = { name = "Health Potion", icon = "icons/potion.png" },
}

local doc = UI:OpenDocument("UI/inventory.rml", "modal")
local dragFrom = -1

local function refresh()
	local view = table.create(SLOTS)
	for i = 1, SLOTS do
		local slot = slots[i]
		view[i] = slot
			and { empty = false, name = ITEMS[slot.id].name, icon = ITEMS[slot.id].icon, count = slot.count }
			or { empty = true, name = "", icon = "", count = 0 }
	end
	doc:SetData("slots", view)
end
refresh()

doc.Event:Connect(function(name, args)
	local i = args[1] -- the 0-based slot index data-for gave the element
	if name == "pick" then
		dragFrom = i
	elseif name == "drop" and dragFrom >= 0 then
		slots[dragFrom + 1], slots[i + 1] = slots[i + 1], slots[dragFrom + 1]
		dragFrom = -1
		refresh()
	end
end)

The icons (UI/icons/sword.png, UI/icons/potion.png) sit next to the document and are chosen per slot with data-attr-src, so adding an item is just a new entry in ITEMS and a new file under UI/icons/. RCSS's drag: clone is what makes the picked-up item's clone follow the cursor while it's dragged; the clone keeps its icon, and dragstart/dragdrop on the source and target slots are how the script hears where it started and landed. A fuller version can add stacking, a click-and-place path for gamepad players, and a Closed handler that reopens the panel; the document and script keep the same shape.

Coming from browser-based game UIs

If you've built game UI as web pages running inside a game, most of what you know carries over. The big change is that there's no JavaScript in the page: the document is markup, styles and data bindings, and your client script plays the part of the page's code.

In a browser-based UIIn Mantle

A CSS fileAn .rcss file, linked the same way. Use dp instead of px; no grid; see Styling for what's different and what doesn't draw.
The page's JavaScriptA client script (Luau, TypeScript, JavaScript or Python) in Scripts/Client/. <script> is refused in documents.
addEventListener("click", ...), onclickdata-event-click="emit('name', value)" in the markup, and doc.Event:Connect(...) in the script.

Component state in a front-end frameworkState lives in your script and goes to the document with SetData. Small UI-only state (the open tab) can live in the document through event assignments.

Canvas, video, WebGLNot available.
Storing things in the page (local storage)A document keeps nothing once closed. Keep state in your script, and save progress on the server.
